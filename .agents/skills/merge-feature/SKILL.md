# Integrar un pull request

1. Identifica repositorio y número de PR. Consulta `gh pr view` con repositorio explícito y campos `state,isDraft,headRefName,headRefOid,baseRefName,mergeable,mergeStateStatus,reviewDecision,autoMergeRequest,isCrossRepository`. Verifica la titularidad, que esté abierto, listo para revisión y sin integración automática. El flujo ordinario es `feature/*` o `fix/*` del mismo repositorio hacia `develop`. Un PR `develop → main` requiere una decisión de lanzamiento de A.
2. Consulta el SHA actual de la rama destino en GitHub y el estado de las ramas y worktrees locales. Obtén la base y el origen si hace falta, sin modificar el checkout ajeno. Verifica que el checkout limpio corresponde al SHA de origen del PR. Si la rama está ocupada o sucia, usa un worktree nuevo con `git worktree add --detach <ruta-nueva> <SHA-origen>`. Revisa el diff con `$code-review`, incluidos riesgos de recursos compartidos. Ejecuta `python3 scripts/feature-status.py <SHA-base> --strict`. En el worktree con HEAD separado añade `--detached-head <SHA-origen>`. Para `develop → main` añade `--release`. Exige validación completa y base actual incorporada.
3. Consulta `gh pr checks --json name,state,workflow,link` y exige `SUCCESS` explícito de `Entorno` y `Juego` del workflow `CI`. Verifica los checks requeridos con `gh pr checks --required` y confirma que corresponden al PR actual. Comprueba conflictos, aprobación humana vigente, conversaciones resueltas y que las reglas efectivas de la rama exijan PR, revisión, checks actualizados y bloqueo de force push. Usa GitHub o sus API de protecciones/rulesets. Si permisos o estados ambiguos impiden confirmarlo, detente. `integrator` puede recopilar evidencia en modo de lectura. Un check ausente, pendiente, omitido, neutral o fallido, una etapa sin configurar o una protección insuficiente bloquea la integración.
4. Ante un bloqueo, explica qué falló y cómo corregirlo en la rama de trabajo. Resuelve conflictos solo con autorización y después de inspeccionar el resultado, ejecutar pruebas y obtener una revisión actualizada. Nunca fuerces un push.
5. Si todo pasa, presenta PR, origen y destino, SHA de ambos, método de merge configurado, revisión, checks y riesgos pendientes. Aplica [`$humanizer`](../humanizer/SKILL.md) al título y al cuerpo del commit resultante. Solicita aprobación de A para ese PR, esos SHA y el mensaje final. Después, vuelve a comprobar los dos SHA, bloqueos, revisiones, reglas y checks. Si algo cambia, evalúa de nuevo y solicita aprobación actualizada. Para una integración normal prefiere squash si está habilitado. Usa merge commit en lanzamientos si la configuración y las reglas lo permiten para conservar la ascendencia de `develop`.
6. Con aprobación, usa una solicitud de merge inmediato al endpoint de GitHub `PUT /repos/{owner}/{repo}/pulls/{number}/merge`, pasando los campos `sha` (SHA de origen revisado), `merge_method` (método permitido), `commit_title` y `commit_message` (texto aprobado). Usa identidad y repositorio verificados. No uses auto-merge, cola ni bypass. Si GitHub exige cola o rechaza el merge inmediato, A decide cómo proceder en GitHub. Una protección con checks sobre base actualizada es obligatoria, dado que el endpoint solo condiciona el SHA de origen.
7. Verifica el resultado con `gh pr view`: estado fusionado, commit resultante y rama destino. Comprueba el CI de destino cuando termine y reporta cualquier fallo. Conserva ramas y worktrees. Si A pide limpieza, verifica que el PR absorbió el trabajo, que no hubo commits posteriores y que el worktree está limpio antes de considerar un retiro sin forzar.
