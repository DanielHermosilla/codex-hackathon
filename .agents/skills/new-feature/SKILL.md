# Implementar una función

1. Entiende qué debe poder hacer el jugador. Lee las instrucciones, el código, las pruebas y los recursos afectados. Identifica dependencias, archivos y dos o tres criterios de aceptación observables. Declara supuestos de bajo riesgo y pregunta solo si la respuesta cambia el diseño o el comportamiento esperado. Si todavía falta elegir o inicializar el motor, acuerda esa decisión con A antes de implementar.
2. Antes de editar, ejecuta `git status --short --branch`, `git worktree list` e inspecciona las ramas y remotos. Para empezar trabajo nuevo usa una referencia verificada de `develop`, preferentemente el `origin/develop` recién consultado. Si la base no existe, coordina la inicialización con A. Comprueba si la rama ya existe localmente o en el remoto y quién la usa.
3. Reutiliza la rama `feature/<nombre>` o `fix/<nombre>` de la tarea si corresponde. Si el checkout está limpio, crea una rama nueva con `git switch -c <rama> <base-verificada>`. Si hay trabajo ajeno o simultáneo, usa un worktree dedicado con ruta nueva en `.worktrees/` o el modo Worktree de la app y confirma la base y la rama. Si Git necesita una escalación, usa la revisión automática configurada. Conserva el checkout y los cambios existentes. Si no se puede aislar la tarea, solicita coordinación.
4. Implementa la solución mínima. Añade una prueba que capture el comportamiento o la regresión. Reproduce primero el fallo si es viable. Comprueba controles, transiciones y casos límite relevantes. Coordina escenas o recursos compartidos. Ejecuta `python3 scripts/validate.py`, la prueba dirigida y, si está disponible, una comprobación del juego en el motor. Registra comandos, resultados y pasos manuales pendientes.
5. Inspecciona el diff completo, incluidos archivos nuevos y recursos. Usa `python3 scripts/feature-status.py <base-verificada>` para comprobar la rama, el alcance y espacios. Verifica archivos sensibles y cambios de generación accidental. Si procede, aplica `$code-review` antes de presentar resultados.
6. Responde en español con comportamiento, cómo probarlo, evidencia y pendientes. Prepara un resumen para el PR. Aplica [`$humanizer`](../humanizer/SKILL.md) al mensaje de cada commit. Muestra el texto final para aprobación específica e incluye solo rutas de la tarea. Con aprobación para publicar, usa un push explícito de la rama a su ref homónima y crea un PR hacia `develop` con la plantilla. Revisa título, destino, archivos y enlace. El PR puede quedar en borrador mientras haya verificaciones pendientes. Termina aquí y deja la integración a `$merge-feature`.
